# Roblox-Game-1

A Roblox game built by a 3-person team. Code is written in **Luau**, synced into Studio with **Rojo**, with dependencies from **Wally**. Tool versions are pinned by **Rokit** (`rokit.toml`).

## Setup (every teammate, once)

```
rokit install        # installs the pinned rojo, wally, selene + stylua
wally install        # downloads Wally packages into Packages/
rojo serve           # then press Connect in the Rojo plugin inside Studio
```

The Rojo Studio plugin is installed per machine with `rojo plugin install`. If that cannot find Studio, download `Rojo.rbxm` from the matching Rojo GitHub release and put it in Studio's plugins folder (`%LOCALAPPDATA%\Roblox\Plugins`).

## Layout

Rojo project: `default.project.json`.

| Disk path         | Studio location                                 | Runs on        |
|-------------------|-------------------------------------------------|----------------|
| `src/server`      | `ServerScriptService.Server`                    | server only    |
| `src/server/vendor` | `ServerScriptService.Server.vendor`           | server only    |
| `src/client`      | `StarterPlayer.StarterPlayerScripts.Client`     | client only    |
| `src/shared`      | `ReplicatedStorage.Shared`                      | both           |
| `Packages`        | `ReplicatedStorage.Packages`                    | both           |
| `ServerPackages`  | `ServerScriptService.ServerPackages`            | server only    |

`Packages/` and `ServerPackages/` are generated by `wally install` and git-ignored. **Never edit them by hand.** `ServerPackages/` only exists when `wally.toml` has `[server-dependencies]`; the Rojo mapping is optional, so a missing folder is fine. `wally.lock` *is* committed.

`src/server/vendor/` holds third-party code copied verbatim into the repo. Do not edit it.

Script file names: `Name.server.luau` (Script), `Name.client.luau` (LocalScript), `Name.luau` (ModuleScript), `init.luau` (folder becomes a ModuleScript).

## Rules

### Language and style
- Luau only. Every file we write starts with `--!strict`. Add type annotations on module APIs.
- Use the `task` library (`task.wait`, `task.spawn`, `task.delay`); never the deprecated `wait`/`spawn`/`delay`.
- Get services with `game:GetService("Name")`.
- Clean up with Trove, handle async/retries with Promise, expose custom events with Signal. Do not leave connections or threads unmanaged.
- Rojo is the source of truth for scripts. Do not edit synced scripts in Studio; changes there are overwritten on the next sync.
- **Code must pass both Selene and StyLua** before you commit: `selene src` and `stylua --check src` (run `stylua src` to fix formatting). Config is in `selene.toml` and `stylua.toml`. Fix the code rather than silencing a lint; vendored and generated code (`src/server/vendor/`, `Packages/`, `ServerPackages/`) is excluded.

### Data and saving
- **ProfileStore is the only way player data is saved.** Server only; require it from `ServerScriptService.Server.vendor.ProfileStore`.
- One server module owns the profile lifecycle. The pattern: `ProfileStore.New(name, template)` once, `StartSessionAsync` on `PlayerAdded`, kick the player if it returns `nil`, `AddUserId` + `Reconcile`, connect `profile.OnSessionEnd` to kick the player, and `EndSession` on `PlayerRemoving` and in `BindToClose`.
- Data in a profile must be plain, serializable values. Add new fields to the template so `Reconcile` backfills them for existing players.
- Use `ProfileStore.Mock` for tests so nothing touches live data.

### Never trust the client with currency
- Currency, inventory, XP, cooldowns and purchases exist **only on the server**. The client may *request* an action; it never sends an amount, a price, or a result.
- The server computes every amount itself and validates every remote's arguments (type, range, ownership, rate) before acting. Replicate state to the client as read-only (attributes, or a remote that only the server fires).
- Assume every RemoteEvent/RemoteFunction argument is hostile.

### DataStore calls
- **Every DataStore call goes inside `pcall`**, with retry/backoff and logging on failure. This includes `DataStoreService`, `OrderedDataStore`, and any ProfileStore call made outside the normal session lifecycle (`GetAsync`, `MessageAsync`, `RemoveAsync`, ...).
- Do not call `DataStoreService` directly from feature code; go through a wrapper that does the `pcall`.

### Visual references and UI styling
- Allowed: imitating style traits of a reference (shape language, outlines, rounded panels, palette mood, layout patterns).
- Not allowed: copying logos, characters, item art, icons, unlicensed fonts, names, or a near-identical recreation of a distinctive screen.
- **Vehicles** (`vault/decisions/0010-vehicle-direction.md`): every vehicle is an original fictional or parody vehicle inspired by real automotive categories, eras and proportions. The rules above still apply in full. In addition:
  1. No real logos, badges, emblems, manufacturer wordmarks or brand fonts anywhere, including on grilles, wheels, plates and decals.
  2. No real model or brand name used unchanged. Every name has a visible parody twist.
  3. Shapes are inspired by the real car (proportions, era, overall vibe), not exact copies of signature grilles, headlight shapes or body lines.
  4. No names that mock a brand in a mean or adult way, and nothing unsuitable for children.
  5. No police, military or emergency-service vehicles or liveries.
  Parody names and removing logos do not establish permission or remove intellectual-property risk, which is not limited to trademarks or trade dress. No legal clearance is established; a commercial release needs a separate review. A parody name with a visible twist, as defined in rule 2, is not a copied name under the rules above.
- "Make it like this" is strong guidance, not a mandate for the whole reference. List the qualities you plan to preserve and have the owner confirm them in the same question batch.
- The representative sample for a visual direction is approved by the repository owner, or by the area owner once the board assigns one. Record the approval in `vault/design/visual-direction.md`. A shop or panel opened during gameplay is reviewed as an overlay on the gameplay view.
- Fonts and touch-target size are undecided. They are proposed after the concept is chosen and the owner approves; do not hard-code them yet.
- The reduced-motion mechanism is an open item, decided with the visual direction after the concept is chosen.
- **Provisional:** UI style tokens (colors, fonts, spacing, corner radius, stroke) live in one shared module in `src/shared`, not in the Studio Style Editor, because that data lives in the place file and is not in Git. Revisit when the concept's visual direction is approved.

### Animation
Setup, settings, tested results and fixes: `docs/ANIMATION_PIPELINE.md`. Reasoning: `vault/decisions/0005-animation-pipeline.md`.
- Free tools only: Blender for keyframes, Mesh2Motion for rigs and a CC0 animation library. No paid animation tools or assets without owner approval.
- Rigid props and UI are animated in code (tweens, springs). Skinned characters and creatures use keyframed bones.
- Roblox bones move and rotate only; bone scale is dropped on import. Squash and stretch on a skinned creature uses translation bones.
- Blender MCP runs with `BLENDER_MCP_SAFE_MODE=1`. Never turn safe mode off; if it blocks a step, stop and tell the owner. Stop the Blender server when you are not using it.
- Test imports go into a local test place, not the Team Create place, with "Upload to Roblox" unticked unless the owner approved the upload.
- Never publish an animation without owner approval. An animation must be owned by the user or group that owns the experience.
- Keep `.blend`, `.fbx` and `.rbxl` test files outside the repo until the team decides where source art lives.

## Team workflow
- `vault/` is the shared Obsidian vault and the source of truth for design, tasks and decisions. Start with `vault/00_INDEX.md` and `vault/tasks/BOARD.md`.
- Before you start work, claim a task on the board. A design-only brief needs a one-line claim too. When you finish, update the board and add a short entry under `vault/log/`.
- Record non-obvious choices as `vault/decisions/NNNN-short-title.md` so the next person does not have to rediscover the reasoning.
- If another session already wrote board or log entries for this work, read them first and merge rather than duplicate. Never rewrite their text, and say in your entry that you built on them.
- **Branches.** `main` is fine for docs, vault, skills, and tooling. From the first game-code task onward, each person works on a feature branch and merges to `main` by pull request only after the GitHub check passes. Branch protection settings are not enforced yet.
- Do not commit build outputs (`*.rbxl`, `*.rbxm`), `Packages/`, `ServerPackages/`, or Obsidian workspace files. `.gitignore` covers these.

### Approvals and planning
Reasoning and history: `vault/decisions/0004-workflow-rules.md`.
- **Owner.** "Owner" means the repository owner until the team assigns area owners on the board at the concept meeting. Area owners then approve samples and plans for their area.
- **Approval.** A one-line "Approved: ..." counts when it clearly refers to a specific request, spec, or ledger. If it is ambiguous which, ask. One reply may grant both a propose-first approval and a plan go-ahead if it says both, for example "Approved, go ahead."
- **Concept selected** means `vault/design/GDD.md` has `status: selected` and `concept:` naming it, plus a decision note. An "Approved:" on a feature never selects a concept. Do not build features for an unselected candidate.
- **Foundations.** Concept-agnostic foundations, starting with the ProfileStore lifecycle module, may start before the concept is chosen. Keep the data template minimal, with no concept-specific fields, until the concept is selected.
- **Propose first**: a new currency, trading, PvP, breeding, permanent loss or theft, paid items or paid luck, cross-server systems, destructive prestige, a different art style, or anything that changes the creative premise. Any currency or economy field is propose-first, not a foundation; that includes a last-claim timestamp for a currency reward. Present player benefit, cost, risk, and a way to test it. Explicit owner approval after that presentation satisfies the rule. Record each approved item as a decision note.
- **Plan before coding.** Post a short plan first: ledger IDs, files, checks. Wait for an explicit go-ahead when the work touches saved data or schemas, the economy, monetization, or shared contracts or interfaces; otherwise proceed. The gates stack: a foundation that touches saved data still needs the plan posted and an explicit go-ahead. A bare "Build X" gets a short intake, then the plan.
- **Failed preconditions.** When a precondition fails, post the questions plus a conditional plan (what you would do once each answer arrives), and do no implementation until the precondition is met.
- **Questions.** Ask every question whose answer would change the result, in one batch, with no fixed cap. Decide reversible details yourself and label them.
